**Ships:** `wise-excavate` v0.1 on npm · the first genuinely useful release

## The announcement

Run one command against a repository you inherited:

```
$ npx wise-excavate stats
```

It tells you three things `git` will not.

**Where the knowledge went.** Not "who committed most" — who _still understands_ each
file. Knowledge decays: someone who touched a file in 2019 and never returned does not
know it today, and someone whose lines were later rewritten by someone else knows it even
less. The files where exactly one person's knowledge still dominates, and that person
stopped committing six months ago, are **knowledge islands** — and they are the parts of
the codebase where the next incident will take twice as long as it should.

**Which files are actually dangerous.** A hotspot is not the biggest file or the
most-changed file. It is churn × complexity × recency × how often changes to it are
_fixes_. Each hotspot is reported with the factor breakdown, because a number you cannot
decompose is a number you cannot argue with.

**Which forty commits out of forty thousand mattered.** Significance ranking that
actively penalises the things naive implementations surface: the Prettier migration, the
licence-header sweep, the lockfile refresh. If the top of that list is a codemod, the
feature is broken — so a test asserts it never is, on every reference repository.

No account. No API key. No configuration. It reads `.git` and nothing else, and every
number it prints is one you can go verify with `git` yourself.

**The screenshot:** `npx wise-excavate stats` on a well-known repository, cropped to the
knowledge-islands section, with the hotspot factor breakdown visible below it. The framing
is _"one command, no install, no account — here is what it found in [repo]."_

## What makes this milestone hard

Rename tracking and identity merging. Everything above is arithmetic; these two are
_judgement encoded as an algorithm_, and both fail silently.

If a rename breaks a file's lineage, half its history disappears — from churn, from
ownership, from the knowledge model — and the report still looks plausible. If identity
merging fails, one person becomes three and the bus factor triples. Neither produces an
error; both produce a confident, wrong answer, which is the one failure mode this product
cannot survive.

That is why M0 shipped deliberate fakes for both, loudly labelled in
`m0-resolvers.ts`, rather than half-real versions. M1 deletes that file.

## Known limitations, carried into M2

Both are P2: recorded, not worked around, and both dissolve when M2 adds hunks.

**The complexity factor is derived from change size** (`hotspots.ts` says so where it does
it), because file content is not in the index until M2. It is therefore strongly correlated
with churn — ripgrep shows factor pairs like `.86/.97` — so the hotspot score behaves closer
to a product of two independent axes than four. It ranks usefully; it is weaker than the
formula implies, and nobody should read a specific score too closely yet.

**`format-only` is never set.** Whitespace-only detection needs the diff body. A codemod is
currently caught by scale plus uniformity, or by a subject that names the tool that made it —
which is what `style: rustfmt everything` needed, since rustfmt's per-file churn is far too
uneven to look uniform. That held on both corpora with zero noise commits in the top fifty,
but a heuristic standing in for a measurement should be named as one.

**Cosmetic:** the cast-of-characters and islands columns align by character count, so a name
containing a double-width character or emoji shifts its row. ripgrep has one
(`Behnam Esfahbod ✅`). Fixing it needs a grapheme-width table, which is not worth a
dependency before the M3 UI exists.

**Cut first if behind:** `--json` output; the cast-of-characters section.
**Never cut:** rename correctness, or the determinism test. Risk R1 is the project's top
existential risk and this is the milestone that contains it.
