## The announcement

Testing Git tooling is miserable in a specific way: the thing you need to assert
against is a graph of content-addressed objects whose hashes change if a timestamp
moves by one second. So people either commit a tarball of a `.git` directory to their
repo and hope, or they write setup code that shells out to `git` forty times and is
impossible to read six months later.

`@excavate/git-fixtures` is the fixture DSL I needed for Excavate, extracted as a
standalone package. You describe a repository and it builds a real one on disk, with
the same object IDs every time, on every machine:

```ts
const fixture = await repo()
  .commit('add the widget', (c) => c.add('src/widget.ts', 'export const x = 1;'))
  .commit('rename it', (c) => c.rename('src/widget.ts', 'src/gadget.ts'))
  .build();

expect(fixture.oid('rename it')).toBe(fixture.oid('rename it')); // across runs, machines, CI
```

Real repositories, not mocks — so `git log --numstat`, rename detection, `.mailmap`
resolution, and blame all behave exactly as they will in production. Deterministic OIDs
because the clock, the author, and the committer are all pinned. It covers the cases
that actually break Git tooling: rename chains, renames across merges, resurrection
(delete a file, add it back later at the same path), revert/re-land pairs, mailmap
identities, CRLF, unicode paths, and empty commits.

It exists because Excavate's single largest existential risk is silently wrong file
lineage — if the tool tells you the wrong history for a file, it has destroyed its own
reason to exist, and it does so quietly. The only defence is a fixture corpus where the
right answer is known by construction. That corpus turned out to be useful on its own.

same commit OIDs visible in a second run below. The point being made visually is

## Post

_"Testing git tooling deterministically"_ — the problem (content-addressed hashes move
under you), the three approaches people take and why each fails, what determinism
actually requires (pinned author, committer, and both timestamps — and why
`GIT_COMMITTER_DATE` is the one everybody forgets), and the fixture matrix that matters
if you are parsing history for a living.

### On that last one

It is not vacuously green. The Linux job ran all 17 test files, including
`fixtures/src/builder.test.ts` (37 tests) and `fixtures/src/matrix.test.ts` (50) — the
suites holding the pinned CRLF and unicode-path golden OIDs.

**The predicted failure did not happen.** Those goldens were expected to break on Linux,
because `core.precomposeunicode` is a macOS-only setting and NFD/NFC normalisation changes a
tree OID. They held, which means the fixture library's environment isolation
(`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, and a scoped `HOME`) does
what it claims across platforms rather than only on the machine it was written on.

One incidental finding: `better-sqlite3` compiles from source under `node-gyp` on the Linux
runners rather than using a prebuild, and it costs nothing measurable — the whole ubuntu job
is 37 seconds.

## What the reference corpora caught

Indexing `rust-analyzer` failed outright with `FOREIGN KEY constraint failed`, and that is
the single best argument for DoD item 1 being a _binding_ requirement rather than a nicety.

`git log --reverse` reverses git's default order, which is by **commit date** — not
topology. A rebase or clock skew produces a commit dated before its own parent, and the
walk then emitted the child first, so `commit_parents.parent_id` referenced a row that did
not exist yet. `rust-analyzer` contains exactly **one** such pair in 12,832 commits.
`ripgrep` contains none, the 24-case fixture matrix contains none, and the 100-commit
walking-skeleton fixture contains none — so every test passed while the walk was wrong.

Fixed by `--topo-order` in `walkArgs`. The regression test builds the condition rather than
the repository (two ref tips, a commit dated months before its parent) and all four of its
assertions were confirmed to fail with the fix reverted.
